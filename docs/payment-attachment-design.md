# 請款附件模組現況盤點與安全設計

## 1. 文件目的與範圍

本文件只整理目前附件模組的實作現況、資料結構、讀取授權邊界、檔案儲存安全設計、候選 API 與待確認規格。

本階段不實作：

- 附件上傳
- 附件下載
- 附件刪除
- Multipart Controller／DTO／Service
- Storage adapter 或檔案系統寫入
- Antivirus／File Signature 掃描
- Attachment audit migration
- V5 Migration
- 附件前端元件與 API client

目前所有上傳、下載、刪除規則均屬設計候選，標示為「待確認」的項目不能直接視為正式契約。

## 3. V2 資料表盤點

來源：`V2__create_payment_core_tables.sql`。

### 3.1 目前欄位

| DB 欄位 | 型別／限制 | 目前用途 |
| --- | --- | --- |
| `id` | `BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY` | 附件 metadata ID |
| `payment_request_id` | `BIGINT NOT NULL`、FK 至 `payment_requests(id)` | 所屬請款單 |
| `uploaded_by_id` | `BIGINT NOT NULL`、FK 至 `app_users(id)` | 上傳者 |
| `attachment_type` | `VARCHAR(30) NOT NULL` | 附件類型 |
| `original_filename` | `VARCHAR(255) NOT NULL` | 使用者原始檔名 |
| `stored_filename` | `VARCHAR(255) NOT NULL` | 受控儲存檔名 |
| `storage_path` | `VARCHAR(500) NOT NULL` | 內部儲存 key／路徑 |
| `content_type` | `VARCHAR(100) NOT NULL` | 檔案 MIME metadata |
| `file_size` | `BIGINT NOT NULL`、`> 0` | 檔案大小 |
| `created_at` | `TIMESTAMP WITH TIME ZONE NOT NULL DEFAULT CURRENT_TIMESTAMP` | 建立時間 |

### 3.2 目前 constraint／index

- `payment_request_id` 與 `uploaded_by_id` 均有 foreign key。
- Migration 沒有指定 `ON DELETE CASCADE`；目前不可假設刪除請款單會自動刪除附件。
- `attachment_type` 有 Check Constraint，只允許目前五個 enum 值。
- `file_size` 有 `CHECK (file_size > 0)`。
- 有 `payment_request_id` index。
- 沒有 checksum／hash 欄位。
- 沒有 soft-delete 欄位。
- 沒有 attachment version 欄位。
- 沒有 upload audit log table。
- V1～V4 為目前既有 Migration；附件擴充若需要 schema 變更，應另行提出 V5，不在本階段建立。

### 3.3 Entity 對齊

目前 Entity 的重要安全邊界：

- `paymentRequest`：`LAZY`、不可為 null。
- `uploadedBy`：`LAZY`、不可為 null。
- `attachmentType`：`EnumType.STRING`，對應 `attachment_type`。
- `originalFilename`、`storedFilename`、`storagePath`、`contentType`：不可為 null，欄位長度與 V2 對齊。
- `fileSize`：`Long`，對應 `BIGINT`。
- `createdAt`：`OffsetDateTime`，於 `@PrePersist` 補值。
- 不繼承 `BaseTimeEntity`，附件只有 `createdAt`。
- 不使用 cascade 或 `orphanRemoval`。

本階段不修改 Entity 或 Migration。

## 5. Metadata 與 Binary Storage 分離

### 5.1 建議邊界

PostgreSQL 只保存附件 metadata；binary file 保存於受控的檔案系統、NAS 或 S3-compatible object storage。現階段不建議把檔案內容存成 PostgreSQL `bytea`，原因是：

- 請款資料庫備份體積會快速增加。
- DB transaction 與大型檔案 I/O 生命週期不同。
- 下載、病毒掃描、容量治理與 object storage 整合較難拆分。

### 5.2 Storage 設定候選

候選設定：

```yaml
payment-approval:
  attachment:
    storage-root: ${PAYMENT_ATTACHMENT_STORAGE_ROOT}
```

規則：

- storage root 只由環境變數或部署設定注入。
- 不把本機絕對路徑、帳密、雲端 access key 或 token 寫入 Git。
- storage root 不回傳給 Frontend。
- DB 的 `storage_path` 應為受控 storage key，不應直接成為可猜測的公開 URL。
- `stored_filename` 應由 Backend 產生 UUID 或同等不可猜測值。
- `original_filename` 只作顯示與下載檔名，不得直接用於檔案系統 resolve。

## 6. 檔名、Path Traversal 與內容安全

### 6.1 檔名處理

不可直接使用以下輸入建立實體檔案路徑：

- `originalFilename`
- Request header 的任意檔名
- Frontend 傳入的 `storedFilename`
- Frontend 傳入的 `storagePath`

Backend 應自行產生 storage key，並在儲存前：

1. 移除或拒絕 `../`、`..\\`、絕對路徑、Null byte。
2. 對 normalized path 執行 `startsWith(storageRoot)` 驗證。
3. 不允許使用者控制目錄層級。
4. 不把 `storagePath` 或 `storedFilename` 放入一般 Detail response。
5. 下載時使用 attachment disposition，並以 RFC 5987 處理非 ASCII 檔名。
6. 防止 CRLF injection，不直接串接未處理的檔名至 `Content-Disposition`。

禁止使用：

```text
storageRoot.resolve(originalFilename)
```

### 6.2 Content-Type 與 File Signature

Browser 傳來的 `Content-Type` 不可視為可信來源。未來上傳流程至少應比較：

- 檔案副檔名 allowlist
- Request `Content-Type`
- 實際 file signature／magic bytes
- 檔案大小與空檔案檢查

目前暫定安全起始 allowlist 候選為：

- `application/pdf`
- `image/jpeg`
- `image/png`

Excel、Word、ZIP、HEIC、WebP 是否允許仍待業務與資安確認。若需要 Apache Tika 或其他檔案型別偵測工具，應先確認 pom dependency 與安全掃描政策，不在本階段加入。

### 6.3 Antivirus 與檔案掃描

目前尚未整合 antivirus。若系統允許使用者上傳外部檔案，正式上線前需決定：

- 是否所有附件都要掃描。
- 掃描失敗是拒絕、隔離還是進入待處理狀態。
- 是否需要 `QUARANTINED`／`SCAN_FAILED` 狀態欄位。
- 掃描服務 timeout、重試與人工處理方式。

目前狀態：`KNOWN RISK`，不得把未掃描的檔案視為可信內容。

## 8. Detail Metadata 與讀取授權

### 8.1 目前 Detail Response

目前 `AttachmentDetail` 回傳：

- `id`
- `attachmentType`
- `originalFilename`
- `contentType`
- `fileSize`
- `createdAt`

目前不回傳：

- `uploadedBy`
- `storedFilename`
- `storagePath`
- 任何公開下載 URL

這個邊界應保留；storage internal data 不應洩漏到一般 UI。

### 8.2 目前 Detail Read Authorization

現有 `PaymentRequestReadAuthorizationService` 以請款單 Detail 的讀取權限作為主要邊界：

| 登入者 | 可讀 Detail 的案件條件 |
| --- | --- |
| Applicant | `paymentRequest.applicant.id = Principal.userId` |
| Supervisor Snapshot | `supervisorSnapshot.id = Principal.userId` 且 `PENDING_MANAGER` |
| `CASHIER` | `PENDING_CASHIER` |
| `PAYMENT_OPERATOR` | `APPROVED` 且 `UNPAID` |

目前沒有獨立附件下載 API，因此不存在附件 binary 的獨立授權。未來下載不得只檢查 `attachmentId`；至少必須同時確認：

1. attachment 存在。
2. attachment 所屬 `paymentRequest.id` 與 path 的 `paymentRequestId` 一致。
3. 登入者具有該請款單的 Detail Read Authorization。
4. 下載的 storage key 屬於查出的 attachment metadata。

案件不存在、附件不存在、path 關係不符或讀取者無權限時，建議統一使用 Not Found 語意，避免洩漏資料存在性；正式 error code 待 API 規格確認。

## 9. 候選 API（尚未實作）

### 9.1 Upload

```text
POST /api/payment-requests/{paymentRequestId}/attachments
Content-Type: multipart/form-data
```

候選欄位：

- `attachmentType`
- `file`
- `version` 或 `expectedVersion`

候選規則：

- 需要 Session Authentication。
- 需要 CSRF Token。
- Actor 一律取自 Backend Principal，不接受 `uploadedById`、`actorId` 或 `userId` 作為授權依據。
- Backend 查出 PaymentRequest 後驗證案件狀態、申請人關係、檔案類型、大小與 storage key。
- 成功時 DB metadata 與 binary 必須具備可恢復的一致性策略。
- 是否增加 PaymentRequest version，待確認。

### 9.2 Download

```text
GET /api/payment-requests/{paymentRequestId}/attachments/{attachmentId}/download
```

候選規則：

- 需要 Session Authentication。
- GET 不需要 CSRF。
- 不接受 `storagePath`、`storedFilename` 作為 query parameter。
- 驗證 attachment 與 path 中 PaymentRequest 關聯一致。
- 使用 `ResponseEntity<Resource>` 或等效串流方式，但不得把 storage root 暴露給前端。
- `Content-Disposition` 預設使用 `attachment`；是否允許 PDF inline 仍待確認。
- 回應 content type 不可只信任使用者上傳時的 header。

### 9.3 Delete

```text
DELETE /api/payment-requests/{paymentRequestId}/attachments/{attachmentId}
```

候選規則：

- 需要 Session Authentication。
- 需要 CSRF Token。
- 只允許規格確認的案件狀態與角色。
- 驗證 attachment 與 path 中 PaymentRequest 關聯一致。
- 是否 soft delete、是否保留 metadata、是否真的刪除 binary，均待確認。
- 需要處理 DB transaction 與 binary delete 失敗的補償流程。

## 10. 上傳、刪除與 Storage 一致性

檔案系統／Object Storage 與 PostgreSQL 不共享同一個 transaction，因此不能直接假設 `@Transactional` 能保證兩者 atomic。

### 10.1 候選上傳順序

建議評估以下流程：

1. 驗證登入者、案件狀態、attachment type、大小與 file signature。
2. 寫入受控 temporary object／temporary file。
3. 產生不可猜測 storage key。
4. 完成安全掃描與必要的 checksum。
5. 將 metadata 寫入 DB transaction。
6. 以 atomic move 或 object storage copy／commit 轉為正式 object。
7. DB 或 storage 任一方失敗時執行補償與清理。

實際順序需配合 storage provider 的 atomicity 能力確認，不能只依賴 Java transaction。

### 10.2 候選刪除順序

需先決定：

- 先標記 DB 再刪 binary。
- 先移至 quarantine／trash 再更新 DB。
- hard delete 或 soft delete。
- delete 失敗時是否由 background cleanup retry。

刪除策略未確認前，不應建立 DELETE endpoint。

## 11. 案件狀態與附件權限候選矩陣

以下只代表待確認設計，不是已實作授權：

| 角色／關係 | DRAFT | PENDING_MANAGER | PENDING_CASHIER | APPROVED／UNPAID | APPROVED／PAID | REJECTED_CLOSED |
| --- | --- | --- | --- | --- | --- | --- |
| Applicant 本人讀 metadata | Allow | Allow | Allow | Allow | Allow | Allow |
| Applicant 上傳 | 候選 Allow | 候選 Deny | 候選 Deny | 候選 Deny | Deny | Deny |
| Applicant 刪除 | 候選 Allow | 候選 Deny | 候選 Deny | Deny | Deny | Deny |
| Supervisor Snapshot | Detail policy | Detail policy | Deny | Deny | Deny | Deny |
| `CASHIER` | Deny | Deny | Detail policy | 待確認 | 待確認 | Deny |
| `PAYMENT_OPERATOR` | Deny | Deny | Deny | Detail policy；`PAYMENT_PROOF` 待確認 | 待確認 | Deny |

需要特別確認的項目：

- Applicant 是否可在送出後繼續讀取附件 metadata。
- 申請人是否可以刪除自己上傳的附件，或只能在 DRAFT 刪除。
- CASHIER 是否能讀取已付款案件的附件。
- `PAYMENT_PROOF` 是否只能由 `PAYMENT_OPERATOR` 在付款完成後建立。
- 付款證明是否允許在 `APPROVED／UNPAID` 先上傳。
- Supervisor／CASHIER 是否只讀 metadata，還是也可下載 binary。
- 是否以 attachment type 進一步限制讀取者。

未確認的情況不得預設為 Allow；正式 API 應採 deny-by-default。

## 12. Audit History 候選設計

候選 action：

- `ATTACHMENT_UPLOADED`
- `ATTACHMENT_DELETED`

目前 `ApprovalAction` 與 `approval_histories` 是否承載附件事件尚未確認。候選方案：

### A. 使用既有 `ApprovalHistory`

優點是沿用現有 Detail 歷程；缺點是 approval history 語意混入 storage lifecycle，且需確認既有 enum／DB Check Constraint。

### B. 新增 `attachment_audit_logs`

優點是語意清楚，可記錄 attachment ID、actor、事件、時間、原因與 storage result；缺點是需要新 Migration 與新 Entity／Repository。

### C. 只保留 metadata 的 `uploadedBy`／`createdAt`

實作較簡單，但無法完整追蹤刪除、失敗、補償與重新掃描事件。

目前不選定 A、B、C，也不修改 `ApprovalAction` 或建立 V5。

## 13. 候選 Error Code

以下只作為 API 設計候選：

| Error Code | 候選 HTTP Status | 情境 |
| --- | ---: | --- |
| `PAYMENT_REQUEST_ATTACHMENT_NOT_FOUND` | 404 | 附件不存在、關聯不符或無讀取權限 |
| `PAYMENT_REQUEST_ATTACHMENT_UPLOAD_FORBIDDEN` | 403 | 不符合上傳角色／案件狀態 |
| `PAYMENT_REQUEST_ATTACHMENT_DELETE_FORBIDDEN` | 403 | 不符合刪除角色／案件狀態 |
| `PAYMENT_REQUEST_ATTACHMENT_TYPE_INVALID` | 400 | attachment type 不在 allowlist |
| `PAYMENT_REQUEST_ATTACHMENT_FILE_TOO_LARGE` | 413 | 超過單檔或 request 上限 |
| `PAYMENT_REQUEST_ATTACHMENT_CONTENT_TYPE_INVALID` | 400 | MIME／副檔名／magic bytes 不符 |
| `PAYMENT_REQUEST_ATTACHMENT_STORAGE_FAILED` | 500 | storage write、move、read 或 cleanup 失敗 |
| `INVALID_CSRF_TOKEN` | 403 | Upload／Delete 缺少或帶錯 CSRF Token |

正式 code 必須與既有 `ApiErrorResponse`、`GlobalExceptionHandler`、前端 `apiError` mapping 一起確認，不在本階段加入。

## 14. 測試計畫（尚未實作）

### Unit tests

- storage key 只由 Backend 產生。
- path traversal、絕對路徑、Null byte、CRLF 檔名被拒絕。
- original filename 不會成為實體 storage path。
- MIME、副檔名與 file signature 驗證。
- file size、空檔案與數量限制。
- attachment type allowlist。

### Service tests

- DRAFT Applicant 上傳／刪除政策。
- 非本人、錯誤案件狀態與不同 authority 被拒絕。
- attachment 與 paymentRequest path 關係不符被拒絕。
- metadata insert／storage write 失敗的補償行為。
- optimistic locking 失敗不留下孤兒 metadata 或 orphan file。
- delete 的 soft／hard delete 行為。

### Controller／Security tests

- 未登入：401 `UNAUTHENTICATED`。
- 無權限：403 或統一 404，依正式規格。
- Upload／Delete 缺 CSRF：403 `INVALID_CSRF_TOKEN`。
- GET download 不要求 CSRF。
- multipart 缺 file、錯誤 type、過大檔案。
- Download `Content-Disposition`、Content-Type、filename encoding。

### PostgreSQL／Filesystem E2E

- metadata 與 binary 成功建立。
- upload 失敗時不留下 metadata。
- metadata 失敗時不留下正式 binary。
- download 只能讀取授權案件與正確 attachment。
- 關聯 ID 不符時不能下載。
- delete 後 metadata、binary、audit 結果一致。
- PostgreSQL 與 storage cleanup／retry 行為。

## 17. 本階段結論

目前附件模組是「DB metadata 已存在、檔案生命週期尚未實作」的狀態。現有 Detail 只讀 metadata，且已由 PaymentRequest Detail Read Authorization 保護；沒有任何附件上傳、下載、刪除 API 或 Storage 寫入程式。

本階段只完成現況盤點與安全設計文件，未修改 Java、Vue、SecurityConfig、Controller、Service、Repository、Entity、DTO、Migration、Database、pom.xml 或 API Contract。等待上述規格確認後，才進入附件功能實作。
